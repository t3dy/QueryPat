# Preservation audit: where QueryPat can lose scholarship

**Audited 2026-09-04.** Companion machine-generated evidence:
[`PRESERVATION_AUDIT_DATA.md`](PRESERVATION_AUDIT_DATA.md), regenerated by
`python scripts/safeguard/audit_regeneration.py --write-report`.

---

## 1. What the architecture claims, and what it actually is

`CLAUDE.md` describes a one-way pipeline:

```
source PDFs → extracted text → unified.sqlite → site/public/data → site/src
                                (authoritative)   (generated, never edit)
```

That is not what the repository does. `site/public/data` is not a generated
artifact. It is **the primary editorial store for a large fraction of the
portal's scholarship**, and it is the only copy.

Forty-three scripts write into `site/public/data`. Only two of them are
exporters. The rest are enrichment, merge, cleaning and repair passes
(`merge_*.py`, `direct_enrich_*.py`, `improve_*.py`, `clean_*.py`,
`fill_content_gaps.py`, `biography/add_*.py`, `fix_dead_links.py`, …) that
write editorial prose *into the exported JSON* and never back into the
database. Several of them read source files (`*.studies.json`, `*.bio.json`)
that are no longer present in the repository.

The consequence: **the database is not a superset of the site data.** Running
the export re-derives the JSON from a database that never received most of the
editorial work, and the result is an impoverished copy that silently replaces
the real one.

## 2. Measured blast radius of a full regeneration

Every exporter was run into a throwaway directory and diffed against the live
tree. A full `export_json.py` run would:

| Effect | Count |
|---|---|
| Live JSON files | 2,704 |
| Files that would **lose content** | **1,048** |
| Files the main export path does not produce at all | 376 |
| Distinct orphaned field paths | 426 |

The largest single loss is the Exegesis close readings:

| Field | Populated in DB | Populated in exported JSON |
|---|---:|---:|
| `segments.concise_summary` | 207 | **880** |
| `key_claims` | — | 1,104 |
| `recurring_concepts` | — | 1,104 |
| `reading_excerpt` | — | 1,104 |
| `people_entities` | — | 880 |
| `texts_works` / `theological_motifs` / `symbols_images` / `tensions` / `evidence_quotes` / `uncertainty_flags` | — | ~879 each |

**673 segment close readings exist only in `site/public/data/segments/`.**
Spot-checked `SEG_EXEG_1975-11-05_SECTION_013_01`: the exported file carries a
full scholarly reading of the Gene Savoy letter — summary, key claims, named
entities, cited scriptures, an evidence quotation. Every one of those fields is
`NULL` in the database.

Other confirmed orphans:

- **Study-topic dossier prose.** `definition`, `pkd_relevance`, `in_the_fiction`,
  `in_the_exegesis`, `intellectual_background`, `scholarly_debate` are written
  into the topic JSON by `merge_studies_topics.py` from `*.studies.json` files
  that no longer exist. A studies export nulls them.
- **Biography enrichment.** `related_works`, `related_letters` and
  `related_exegesis_entries` in `biography/events.json` are produced by no
  exporter.
- **Works pages.** Several `works/*.json` files carry `card_summary` /
  `page_summary` for slugs that have **no row in the `works` table** at all,
  plus fields such as `critical_caution` that the table has no column for.
- **`exegesis/works/*.json`** (15 files: `theological_headline`, `intro`,
  `theological_synthesis`) have no backing table anywhere in the schema.
- **`connections.json`, `scholars.json`, `essays/index.json`, `themes/`,
  `people/`, `letters/`** are not produced by the main export path.
- **Claim-ID leakage.** The database's own `terms.definition` contains inline
  `(CLM_S_…)` ids. They are stripped *after* export by
  `clean_dictionary_claim_leaks.py`. Export without that pass and the leaked ids
  reappear on public pages.

## 3. Risk register

| # | Hazard | Mechanism | Severity |
|---|---|---|---|
| R1 | Full export erases 673 Exegesis close readings | DB has no source for them | **Critical** |
| R2 | Studies export nulls dossier prose | `*.studies.json` sources deleted | **Critical** |
| R3 | Biography relations vanish | no exporter emits them | High |
| R4 | `CLM_*` ids leak into public prose | cleaning is post-export, not in DB | High |
| R5 | Editorial work destroyed before it is ever committed | no snapshot before regeneration | High |
| R6 | An impoverished regeneration gets committed | nothing compares a commit against HEAD | High |
| R7 | Producers of 376 files are undocumented | must be rediscovered by grep | Medium |
| R8 | `seed_*.py` / `scan_corpus.py` `DELETE FROM study_passages` by topic | intended, but unguarded | Medium |

| R10 | 3 segment JSON files are malformed and fail to parse | pre-existing corruption, invisible | Medium |

## 4. The governing principle

> Generated artifacts may be regenerated. **Research artifacts and editorial
> artifacts are append-only, versioned and archived** unless a destructive
> operation is deliberately requested.

The problem is that QueryPat has no way to tell the two apart. Until every
orphaned field is round-tripped back into the database, the safe assumption is:

> **Any populated field in `site/public/data` may be irreplaceable.**

## 5. What was built in response

See [`PRESERVATION.md`](PRESERVATION.md) for the mechanisms, and
[`RESEARCH_WORKLOG.md`](RESEARCH_WORKLOG.md) for the research-trail convention.

| Risk | Mitigation |
|---|---|
| R1–R3, R5 | `scripts/safeguard/safe_export.py` — snapshot, export, diff, auto-restore anything that lost content |
| R4 | post-export cleaning passes run inside `safe_export.py`; a guard asserts no `CLM_` in public prose |
| R6 | `scripts/safeguard/check_data_diff.py`, installed as a `pre-commit` hook, blocks commits that remove content |
| R1–R11 | `scripts/safeguard/snapshot.py` — timestamped, manifested archives with a committed ledger |
| R7 | this document, plus `docs/PRESERVATION_AUDIT_DATA.md`, regenerable on demand |
| R11 | `archive/<date>/` structure and the worklog convention |

## 6. What is still unsafe

- The orphaned fields are still orphaned. The mitigations prevent *loss*; they
  do not restore the database as the source of truth. Round-tripping the 673
  close readings, the dossier prose and the biography relations back into
  `unified.sqlite` is the real fix and has not been done.
- `--allow-destructive` and `git commit --no-verify` both still exist. The
  guards raise the cost of destroying work; they cannot make it impossible.
- Snapshots are local. They protect the working tree, not a lost machine.
- The three malformed segment files have not been repaired; repairing them
  requires reconstructing content that may itself be irreplaceable.
